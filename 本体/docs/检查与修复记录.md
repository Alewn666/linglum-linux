## 第 2 轮（2026-10-26）：自装盘持久化端到端打通 ALL PASS 9/9，修 3 个引导 bug

### 结论
`install-linglum` 把 Linglum 装进 GPT 硬盘后，**只挂硬盘能启动、写文件、重启后文件还在**——持久化闭环。KVM e2e `test_linglum_install.py --kvm` **9/9 ALL PASS**。修掉 3 个互相独立的引导 bug（细节见下）。产物 `out/linux.iso` md5 `6676f78d37544b58c2bb9ea8daa42f77`（88MB）。

### 前置：TCG 写 194MB 太慢 → 改用 KVM
- 现象：阶段 A「Linglum 写入完成」在 TCG 下 300s、放宽到 600s 仍超时（`/tmp/ling_e2e*.log`）。
- 排查：宿主 `zcat install/linglum.img.gz > /dev/null` **仅 1.9s**（gz 完整、203423744 字节精确）→ 解压不是瓶颈；卡在 TCG 软件模拟下往 virtio 盘写 194MB 真实数据（非全零，比 LoongOS 的 129MB 全零慢一个量级）。
- 处置：e2e 改 `--kvm`（`sudo -n`，host CPU，GIC v3）。`/dev/kvm` root-only、`sudo -n` 免密可用。KVM 下阶段 A 秒级完成。

### Bug 1：GRUB `search --part-uuid` → `unspecified search type`
- 现象：阶段 B 磁盘引导落到 `grub>` 应急 shell。
- 诊断（`diag_grub.py`，boot 到 grub> 逐条探针）：`ls (hd0,gpt1)`=FAT `ESP`、`ls (hd0,gpt2)`=ext* `linglum`、`ls (hd0,gpt2)/boot`=`Image` —— **分区/文件全对**；但 `configfile /grub.cfg` 报 `error: unspecified search type.`。
- 根因：本机 arm64 GRUB **没有 `search_part_uuid` 模块**（`ls /usr/lib/grub/arm64-efi/` 只有 `search / search_fs_file / search_fs_uuid / search_label`）。
- 修：grub.cfg 改 `search --no-floppy --set=root --label linglum`（`search_label` 在位）。**内核 cmdline 的 `root=PARTUUID=` 不动**（Linux 内核原生支持 GPT PARTUUID，与 GRUB 用什么搜无关）。

### Bug 2（独立）：grub.cfg 放在 memdisk 根，GRUB 去 `(memdisk)/boot/grub` 找
- 现象：Bug 1 修完，`configfile /grub.cfg` 手动能出菜单（`Linglum` 条目 + 3s 倒计时），但**自动引导仍进 `grub>`** —— 证明配置内容对、是加载路径错配，与 search 无关的第二个 bug。
- 诊断（决定性探针）：`echo $prefix` → `(memdisk)/boot/grub`；`echo $prefix/grub.cfg` → `(memdisk)/boot/grub/grub.cfg`；而 `ls /boot/grub` 只有 `fonts/ locale/ arm64-efi/`，`ls /` 才看到我们的 `grub.cfg`。GRUB 的 `normal` 找 `$prefix/grub.cfg` 落空 → shell。
- 修：`grub-mkstandalone ... "boot/grub/grub.cfg=$GRUB_CFG"`（graft point 指定目标路径）。离线验证：`strings build/mkinstall/BOOTAA64.EFI` 出现 `%s/grub.cfg` + `boot/grub/...` 前缀 + 新 cfg 内容。

### Bug 3：无 initrd 启动，内核不自动找 `/init` → `No working init found`
- 现象：Bug 1+2 修完，内核起来了但 `Kernel panic - not syncing: No working init found. ... Run /bin/sh as init process`。
- **我先判断错、后被证据纠正**：一开始归因"缺 `/bin/sh` 软链"。反证三条——①`/init` shebang 是 `#!/bin/busybox sh`（**不依赖 /bin/sh**）；②Live 用**同一个 init**、`rootfs/bin` 软链数也是 **0**，却能启动；③`debugfs dump /bin/busybox` md5 与源文件一致（`1c7851ce…`，未被 mke2fs 损坏）。
- 真根因：**Live 有 initrd**（内核跑 rootfs 里的 `/init`）；**装机无 initrd**，内核挂载 ext4 后不自动找 `/init`，只走回退链 `/sbin/init→/etc/init→/bin/init→/bin/sh`，这些在装机根里一个都没有（0 软链）→ 全失败 → panic（末行 `Run /bin/sh as init process` 正是回退链最后一环）。
- 修：内核 cmdline 加 `init=/init`，显式指定（与 Live 行为一致）。

### 离线排查利器（本轮学会，别再烧 VM 猜）
- **`diag_grub.py`**：boot 到 `grub>` 逐条发探针（`echo $root/$prefix`、`ls` 各分区、`configfile` 手动加载、`normal`），把 GRUB 看到的东西全打出来。定位 Bug 1/2 全靠它。
- **`debugfs` 离线验 ext4**：`debugfs -R "ls -l /" root.ext4` / `-R "stat /init"` / `-R "dump /bin/busybox /tmp/x"` 再 `md5sum` 对比。定位 Bug 3 全靠它，零 VM 开销。
- **`cleanup_qemu.sh` / `kill_orphan.sh`**：把 kill 逻辑写进**文件**再 `sh` 执行，避免 `pkill -f` / 命令行含匹配模式**把执行 shell 自己杀掉**（本轮踩了 3 次 `-9` 自伤）。被 sudo 起的孤儿 QEMU 普通用户 kill 会 EPERM，要 `sudo -n kill`。

## 第 1 轮（2026-10-25）：Live 安装盘从零打通，端到端 7/7

### 目标（用户定调）
1. `/vol1/1000/项目/loongos/iso/Linux内核ISO/linux.iso` = **Linux 内核做的 Live 安装盘，用来安装纯自研 LoongOS**。
2. Linglum 本身**是一个操作系统**（灵珑系统的 Linux 内核路线），安装 LoongOS 是附带能力。

### 做了什么
| # | 事项 | 关键做法 |
|---|---|---|
| 1 | 内核 | 用户提供的 `linux-aarch64-rc-7.3.rc7-1-aarch64.pkg.tar.xz`（Arch ARM 包）→ 取 `boot/Image`（51MB，arm64，EFI stub）。原自编译路线（686/≈2000 单元）经用户叫停。 |
| 2 | 内建驱动核查 | `strings Image \| grep -w` 验证 **xhci_hcd / usbhid / hid_generic / virtio_pci / virtio_blk / virtio_console / efifb / pl011 / fbcon 全部内建**（不需要模块，initramfs 里没有 .ko）。 |
| 3 | 用户态 | BusyBox-static 1.35（Debian deb）+ 自研 `init`（挂 proc/sys/devtmpfs，tty1 与 ttyAMA0 各一个 shell）。 |
| 4 | 安装素材 | `install/disk.img`（65MB）= 1MB 偏移 + 64MB FAT32 ESP（`EFI/BOOT/BOOTAA64.EFI` + `kernel.elf`），MBR `type=ef,bootable`。宿主机用 `mkfs.vfat + mcopy + sfdisk` 预制。 |
| 5 | 安装器 | `install-loongos`：`dd if=/loongos/disk.img of=$DEV bs=1M conv=fsync`，要输入 `yes` 确认。**不用 busybox mkfs**（Debian 的 busybox 没有 mkfs.vfat applet）。 |
| 6 | ISO | `grub-mkrescue`，menuentry 用 ASCII（GRUB 字体无中文字形）。 |

### 发现的坑（都已修）
1. **QEMU 不显式加载 AAVMF 固件 → 串口零输出**（首跑 200 秒只收到 71 字节超时消息，误判"ISO 坏"）。
   正解：`-drive if=pflash,format=raw,readonly=on,file=/usr/share/AAVMF/AAVMF_CODE.fd`
   ＋ 一份可写 `AAVMF_VARS.fd` 副本。**这是本轮最耗时的坑。**
2. **motd 只打到 tty0**：`console=ttyAMA0 console=tty0` 时 `/dev/console` 取最后一个 → 串口看不到横幅。
   修：init 里分别 `cat /etc/motd > /dev/tty1` 和 `> /dev/ttyAMA0`。
3. **GRUB 中文菜单标题变空白**（无 CJK 字形）→ 标题改 ASCII；fbcon 同理，motd 以英文为主。
4. **busybox 无 mkfs.vfat** → 安装器改 dd 预制镜像，零格式化依赖。
5. **`/bin/sh` 是 dash，不支持 `{}` 花括号展开** → `mkdir rootfs/{bin,sbin}` 造出字面量目录
   `rootfs/{bin,sbin,...}`（清理过一次又犯一次，已彻底清）。
6. **NAS 于 11:33 自行重启**（uptime 8 分钟、`/tmp` 被清），第一次 E2E 中途夭折。
   处理：测试产物全部挪到 `build/`（不再用 /tmp）；QEMU 内存 768MB → 512MB（当时 zram 吃满）。

## 第 2 轮（2026-10-25 14:20）：安装向导「列表全空 / write failed at block 0」修复 ✅（离线验证）

## 第 3 轮（2026-10-25 15:00）：内存/光盘两条线全错 → 压缩流式方案 ✅

**现象链**：用户截图 `write failed at block 0` → 修好后测试又连续报

3. 测试脚本 `-cdrom` 与 `-drive if=none` 并用时 **/dev/sr0 不会创建**

1. **guest 里的磁盘名 ≠ 宿主机 XML 的 dev 名**：XML 写 `sdb`，guest 里是 `sda`（光盘变成 `sr0`）。
   一律用 `ls /sys/block` 或 `/sys/block/*/device/model` 认盘。
2. **硬断电前必须 `sync`**：第一次写 `/home/persist.txt` 后直接 `virsh destroy`，重启后文件没了
   （页缓存未落盘）；补 `sync` 后复测通过。
